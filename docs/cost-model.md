# 成本模型：钱花在哪，动哪里才有用

> 这份文档只做一件事：**把"该动哪一刀"建立在数字上**，而不是感觉上。
> 所有数字都可复算——用 `tools/exec/session-stats.mjs` 对自己的会话跑一遍。

---

## 1. 长会话的账：输入占绝对多数，而输入的大头是"把上文再发一遍"

来自一次真实长会话的分析（422 轮 / 6,273 次模型调用）：

| 口径 | 数值 |
|---|---|
| 输入占成本 | **99.4%** |
| 其中"**把上文再发一遍**"（历史重发） | **76.4%** |
| 其中固定开销（系统提示 + 二十几个工具定义 + 技能描述 ≈ 3.8 万 tok/次） | 23.6% |
| 缓存命中率 | **99.1%**（5,694 / 5,695 次调用命中） |

推论：**省 token 的唯一大杠杆在"重发"上**。
分层记忆之类的优化压的是"固定开销"里的一块（3.8 万 → 约 3.1 万 tok/次，约 −20%），
但**对 76.4% 那一块毫无影响**。

---

## 2. 为什么会重发这么多

| 事实 | 数值 | 含义 |
|---|---|---|
| 一条内容进历史后，平均被重发 | **63.8 次** | 你写的每个 token 都要乘 64 |
| 工具分布（按重发占比） | Read 19.7% ｜ Bash 13.7% ｜ Edit 8.2% ｜ Write 6.1% | 前三名都是"读"和"跑命令" |
| 思考 reasoning 占重发 | **27.1%** | 中间思考被反复投喂，对下一次生成帮助有限 |
| 工具调用参数占重发 | **17.7%** | 含 Edit/Write 的正文 |
| 文件被读过不止一次 | **53%**（`main.py` **62 次**） | 重复读 |
| 读取后 2 次调用内文件被改 | **40.4%** | 那份快照**版本已过期**——留着不只是没用，是**错的** |

---

## 3. 三条杠杆（按收益排序）

| 杠杆 | 实测依据 | 手段 |
|---|---|---|
| **① 转数** | 调用数 ×0.6，收益是第二名的两倍 | 组合型操作固化成执行器（一行调用 = 一轮） |
| **② 每轮上下文体积** | `Read` 带 limit → ×0.86 | 读前先 grep、必带 limit、输出去字节留结论 |
| **③ 重复读** | 53% 的文件被读过不止一次 | 同文件不重复读、大探索走子代理 |

四条动作叠加后的等效成本：**1.117 亿 → 0.524 亿（省 53%）**。

---

## 4. 一条红线：绝不能"把历史压缩重写"

缓存命中率 99.1% 意味着**大部分输入走的是低价档**。
任何改写**已缓存前缀**的动作，**等于把最便宜的部分变成最贵的** ——
表面积变小了，账单反而上升。

> 直接的后果：**"回头把历史压一压再重拼"是错的**。
> 正解是：只对"今后新产生的内容"节流，绝不动已经缓存的前缀。

这条也是"为什么 `brief` 是给**新会话/新任务**用的，而不是每轮回头看历史用的"。

## 5. 外部研究（用来定方向，不是用来抄数字）

| 来源 | 结论 |
|---|---|
| **JetBrains《The Complexity Trap》**（SWE-bench） | **观察掩码**：成本 −52%，solve rate **+2.6%**；**LLM 摘要**：成本 −50% 但轨迹长 13–15%，且**降低**正确率（摘要抹平了"该收工"的信号） |
| **CodeAct**（ICML 2024，17 个模型） | 成功率最高 +20%，动作数 −30% |
| **Anthropic code execution with MCP** | 官方例子 150k → 2k token（**−98.7%**） |
| **Microsoft Agent Framework CodeAct** | 耗时 −52.4%，token −63.9% |
| **Anthropic 多代理研究系统** | 多代理 ≈ **15× chat token**（单代理 ≈ 4×）；官方原话：多数编码任务可并行度低于研究，且 agent 间实时协调还不成熟 → **不要做 swarm** |

**读法**：掩码（框架层）与 CodeAct（执行器层）都被独立验证过；
而"LLM 摘要"这条最直觉的路**被实测否掉了**——这正是本设计不走"摘要压缩"的原因。

## 6. 本项目的实测基线

用 `session-stats` 对一个真实开发会话（本仓库开发过程本身）跑出来的数：

```bash
node skill/tools/exec/session-stats.mjs <session.jsonl>
```

```
OK    23 轮 · 475 次模型调用 · 输入 66,341,881 tok
KEY   cache-read=98.3%
KEY   resend(历史重发)=73.0%
KEY   top-tools=Bash:263,Edit:127,Read:107,Write:73,TaskUpdate:12
KEY   biggest=Read:35700
```

读法：**73.0% 的输入 token 是历史重发**；`Bash` 与 `Read` 合计 370 次调用，
正是杠杆①②③要动的地方；单条最大的工具返回 35,700 字符（一次全量 `Read`）。

**改了什么之后，用同一条命令复量** —— 这就是把"感觉变快了"变成"数字变好了"的办法。

## 7. 口径说明（避免误读）

- `input_tokens` **已包含** `cache_read_input_tokens`，所以"历史重发占比"是
  `(累计输入 − 最小输入 × 调用数) / 累计输入`，是一个**估算**（把最小输入当作固定开销）。
- 一次模型调用会拆成多条事件、每条带同一份 `usage`，所以必须按 `messageId` **去重**，
  否则调用次数会被高估数倍。
- 缓存单价低于未命中输入，所以"等效成本"不能只按 token 数乘算；
  上面的 53% 是按实际单价折算过的。
