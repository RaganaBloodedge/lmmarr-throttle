# 设计：lmmarr-throttle

> 名字共识：**`lmmarr-throttle`**（会话内上下文节流）。
> 与之配套的是已发布的 **`lmmarr-memory`**（跨会话任务记忆）——
> 两者**共用同一份冷存储**（`.workbuddy/memory/`），不抢目录。

---

## 0. 一句话

**主上下文只装「结论 + 指针」。** 过程、原文、失败重试——
要么**不进**（子代理），要么**压掉**（执行器），要么**可回收**（冷存储 journal）。

## 1. 需求来源 → 落地物（逐条对照）

这一节是这份设计的核心：**每一条都是先提出的原始要求，右侧是它在代码里的落点**，
没有一条停在"写在文档里"。

| # | 原始要求 | 落地物 | 在哪 |
|---|---|---|---|
| 1 | 「很多历史对话不应该直接重复投喂给 LLM，而是根据任务描述和索引找到本地冷存储的历史对话，**重新拼成一段指引性的**，回喂给 LLM」 | `brief` 命令：按任务 + 关键词从冷存储拼 ≤1200 字符指引，**零 LLM 调用** | `scripts/brief.js` |
| 2 | 「不应该记录完整的路径或行动和执行结果，应该是**某条指令 + 结果**，中间的过程不应该保存」 | journal 条目的粒度与形状就是「指令 + 结果」；`did/pit/open` 三类 | `scripts/journal.js` |
| 3 | 「中间的过程不应该保存」→ 由代码强制，而不是靠纪律 | 条目**必须单行**、**≤400 字符**，超了直接报错 | `assertEntryText()` |
| 4 | 「出现报错了，应该只返回报错，而且在**解决报错后就不要记录这条详细的报错**，而是只保留关键信息，总结性的」 | `resolve` 命令：`open #N` → `pit #N`，**丢弃报错原文**，强制要求 `--keep` 写总结 | `resolveEntry()` |
| 5 | 「中间很多没用的思考结果也被投喂到上下文中，完全没有用」 | 思考没有任何入口能进 journal（只有 `did/pit/open`，且单行限长） | 同上 |
| 6 | 「应该主要靠**冷存储和冷存储的良好结构**来减少 token 的消耗」 | 复用 lmmarr 的 `.workbuddy/memory/` + 新增 `JOURNAL_<id>.md`；格式契约由测试钉住 | `references/journal-format.md` |
| 7 | 「skill **内置判别机制**，看看当前的 Agent 框架支不支持子代理，如果有子代理就把探索任务交给子代理，如果没有子代理，就只在探索完成时保留结果和关键节点，不要保留探索过程中的全部过程信息，比如说执行的代码之类的和长串的信息」 | `agents-probe.mjs` → `MODE delegate\|self-compress`，两条路线各自的纪律成文 | `tools/agents-probe.mjs` |
| 8 | 「调试并不会变难，因为**失败时再返回整段结果**」 | 执行器**双模**：成功压 ~10 行，失败吐全量 stderr + 最小复现 | `scripts/protocol.js` |
| 9 | 「一次性任务可以不划算……**短程任务可以不启用**这个 skill，当足够长的时候才会触发」 | SKILL.md 写明触发条件；skill 加载模型本身不启用时零成本 | `skill/SKILL.md` |
| 10 | 「大探索走子代理真行，**子代理的任务不需要在主流程中重复**」 | 委派契约：brief 自包含 + 返回只回结论与指针 | `references/discipline.md` |
| 11 | 「冷存储是我已经开发的 lmmarr 的功能」 | 不重造；只读同一份 `MEMORY_<id>.md`，格式契约用测试对齐 | `scripts/taskdoc.js` + `tests/taskdoc.test.js` |
| 12 | 「子代理能作为一个 skill 实现吗……感觉还需要 multi-agent 技术彻底地解决这个问题」 | 结构性的答案：**不能**，且需要的是「隔离 + 强制」而不是 multi-agent | 见本文 §3、§4 |

## 2. 三条杠杆与三条红线

### 杠杆（按收益排序）

| 杠杆 | 手段 | 依据 |
|---|---|---|
| **① 转数** | 组合型操作固化成执行器（一行调用 = 一轮） | 调用数 ×0.6，收益是第二名的两倍 |
| **② 每轮上下文体积** | 读前先 grep 定位、`Read` 必带 limit、输出去字节留结论 | `Read` 带 limit → ×0.86 |
| **③ 重复读** | 同文件不重复读；大块探索走子代理 | 53% 的文件被读过不止一次 |

### 红线（反直觉，勿踩）

1. **绝不"把历史压缩重写"。** 实测缓存命中 **99.1%**，改写**已缓存前缀**等于
   *把最便宜的部分变成最贵的*。正解：只对"今后新产生的内容"节流，不动已缓存前缀。
2. **绝不静默截断。** 丢东西必须说出来（`brief` 已内建截断提示）。
3. **绝不把读回来的东西写回记忆。**

数字口径与来源见 [`cost-model.md`](cost-model.md)。

## 3. 三个原语与它们的容器

**问题**：子代理能不能做成 skill？

**答案：不能，而且是结构性的。** skill 的清单只有 `name` + `description`，
它没有声明子代理或钩子的字段；skill 和它的 `scripts/` 里**没有 LLM**——
脚本是普通 OS 进程，没有 LLM 就不可能"是"一个 agent。

| 原语 | 是什么 | 声明在哪 | 强制力 |
|---|---|---|---|
| **Skill** | 静态说明 + 脚本，加载进**当前**上下文 | `SKILL.md`，或插件的 `skills/` | **仅建议**（模型可以选择不听） |
| **Agent（子代理）** | 独立 agent 实例，**自己的上下文窗口**，只有最终消息回父级 | 插件的 `agents/*.md`；另有内置 Explore / Plan / general-purpose | **隔离**（过程物理上回不来） |
| **Hook** | 生命周期事件触发，配置在上下文之外，确定性 | 插件的 `hooks/hooks.json` | **强制**（不经过模型判断） |

**硬证据**：本机 `workbuddy-docx` 插件的 `.codebuddy-plugin/plugin.json` 同时声明三者：

```json
{
  "hooks": "./hooks/hooks.json",
  "skills": ["./skills/brief-compose", "..."],
  "agents": ["./agents/doc-converter.md", "./agents/doc-formatter.md", "./agents/doc-writer.md"]
}
```

### 三条推论

1. **skill 能"指挥"子代理**：SKILL.md 写清"何时委派、brief 怎么写、返回什么契约"，
   主 agent 读后去调内置的 Agent 工具。这是"子代理用法做成 skill"唯一真实的形态——
   **它是说明书，不是执行体。**
2. **skill 不能"成为"子代理。**
3. **要"彻底解决"必须上插件层**：**"彻底" = 隔离（子代理）+ 强制（hook），
   不是"multi-agent"。**

## 4. 四层能力

```
L4 委派   大探索走子代理      → 过程永不进主上下文（50k in / 1.5k out）
L3 沉淀   journal + brief     → 让「删」变安全
L2 纪律   grep / limit / 并行 → 每轮体积 ×0.86、消除重复读
L1 执行器 固化成脚本，一行调用  → 转数 ×0.6（第一杠杆，收益最大）
```

| 层 | 状态 |
|---|---|
| L1 执行器 | ✅ `tools/exec/session-stats.mjs` 已实装 + 协议成文 |
| L2 纪律 | ✅ 成文（`references/discipline.md`）—— **建议层，无强制力** |
| L3 沉淀 | ✅ journal + brief 已实装 |
| L4 委派 | ⚠️ 能力门已实装；**委派本身靠模型调用内置子代理**，本 skill 只提供契约 |

**执行器的判据**：同一模式写到**第二次**就固化。预置执行器的源码 **0 次**进历史；
现场写的脚本要先花几十行进历史，再被重发几十次才摊得平。

## 5. 探索性工作：两条相反的需求

探索不是"一种工作"，是**两段**，需求正好相反：

| 阶段 | 需要什么 | 为什么 |
|---|---|---|
| 探索**中**（live） | 观测必须**在** | ReAct 每步依赖上一步的观测，删了就走不下去 |
| 探索**后**（done） | 轨迹必须**走** | 留着每轮重发；而且 **40.4% 的读取在 2 次调用后文件已变**——"留着不只是没用，是**错的**" |

**问题的真身**：探索从不"宣布结束"，所以轨迹永远停在 live 状态，一直被复用。
→ 要的是**退休机制**，不是"少探索"。

### 三条退休路径

| 路径 | 机制 | 适用哪种探索 | 谁执行 |
|---|---|---|---|
| **进不来** | 执行器（预固化脚本，输出 ~10 行） | 可**预先指定**的探索 | skill `scripts/` |
| **出不去** | 子代理（隔离，只回结论） | **自包含**的——宽并行或深串行都算 | 内置 Agent 工具 |
| **就地退休** | 掩码（滚动窗口 → 占位符/指针） | 必须留主线的**逐步依赖型** | **框架 / hook** |

**一个必须纠正的框定**：子代理不是只给"宽并行探索"用的。
**单个子代理跑串行深挖、只回结论同样成立**——没拿到并行，但拿到了**隔离**。
代价是每个子代理的固定开销（自带 system prompt + **首请求不吃父级 cache**），
但**单子代理远比 fan-out 便宜**（fan-out 才是 15×）。

### 真正不能委派的残留

只有"主流程必须**逐步消费每个中间结果**"的那种。对这种，**只有掩码能救，而掩码是框架层能力**——
模型改不了自己已进窗口的旧观测。skill 只能做两件半：

1. **带问题去探索**：探索前写下一句"这次要回答什么"。问题答完 = 退休点。
2. **答完即登记**：结论落 journal + 指针，**停止引用原文**。
3. （半件）**压缩入口体积**：grep 定位再读、带 limit、不重复读。

### 为什么"垃圾被复用"不只是花钱

JetBrains《The Complexity Trap》实测：**掩码让 solve rate +2.6%**；
而 **LLM 摘要反而降低它**（摘要抹平了"该收工"的信号）。
→ 退休不只是省钱，是**提高正确率**——陈旧观测会误导，模型得从 50k 陈迹里翻那 1k 有效信息。

### 掩码与 cache 的冲突怎么解

掩码会改写已缓存的前缀 —— 所以**必须批处理**：攒到阈值一次性退休一大批，
付一次重读，随后重新缓存。**绝不能每轮掩一点。**

## 6. 诚实交代：本 skill 治的是"入口"，不是"窗口"

| 能做 | 做不到 |
|---|---|
| 压**入口**：执行器、grep+limit、不重复读 | ✗ 让**已经在窗口里**的旧观测消失 |
| 把结论沉淀成 journal + 指针，此后不再引用原文 | ✗ 改写已缓存的前缀（会反而更贵） |
| 用 brief 让新会话**不去重读**历史 | ✗ 在会话中途"回填"压缩 |

准确的说法：**skill 管"入口"，框架管"窗口里"。**
这也解释了为什么"彻底解决"的下一步是插件层。

## 7. 与 lmmarr-memory 的关系

| 能力 | 归属 | 形态 |
|---|---|---|
| 跨会话任务结构（索引 + 关系图 + 进度） | `lmmarr-memory` | skill（已发布） |
| `JOURNAL_<id>.md` 会话日志（指令 + 结果） | **`lmmarr-throttle`** | skill（本项目） |
| `brief` 冷存重建 | **`lmmarr-throttle`** | skill（本项目） |
| 执行器库 + 输出协议 | **`lmmarr-throttle`** | skill（本项目） |
| 能力门（有无子代理） | **`lmmarr-throttle`** | skill（本项目） |
| 强制 + 自定义子代理 + hook | 待定 | **插件**（若要"彻底"） |

两者**共用同一份冷存储**，可以只用其一。同时用时：先 `brief` 再干活，干完往 `journal` 追加。

## 8. 岔路（尚未拍板）

| 路线 | 得到什么 | 代价 |
|---|---|---|
| **只做 skill**（当前） | 轻、快、跨项目可用、零构建 | 全是**建议**，模型可以不听；压不了"窗口里" |
| **打成插件** | 能声明 `agents/`（自定义子代理）+ `hooks/`（强制），可做掩码 | 打包与维护变重 |

**当前选择**：先做 skill，但把语义与脚本设计成"将来能原样升格为插件的 agents/hooks"。
第一步轻，第二步不用重写。
