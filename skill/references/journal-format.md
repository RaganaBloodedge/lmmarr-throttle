# journal 格式与报错生命周期

## 文件

```
<记忆目录>/JOURNAL_<任务ID>.md
```

与 lmmarr 的 `MEMORY_<任务ID>.md` **同目录**（默认 `.workbuddy/memory/`），两套共用同一份冷存储、不抢目录。

分工：

| 文件 | 回答 | 性质 |
|---|---|---|
| `MEMORY_<id>.md` | 这个任务**现在怎么样了** | 可重写（由 lmmarr 维护） |
| `JOURNAL_<id>.md` | 这个任务上**发生过什么** | **append-only** |
| `MEMORY.md` | 有哪些任务、彼此什么关系 | 索引，由 lmmarr 生成 |

## 文件形状

```md
# 会话日志 · api-retry

> append-only。只记「指令 + 结果」；不记路径、不记过程、不记原文。
> 唯一允许的改写：`open` 解决后降级为 `pit`（丢弃报错原文）。

- did  #1  改用指数退避，基准 200ms
- pit  #2  熔断器默认半开窗口太短 → 误放流量；特征=短突发被放行；处理=调到 30s
- open #3  并发压测下 P99 抖动未定位（复现：50 并发连跑 10 分钟）

## next

补熔断器单测
```

## 四类条目

| 类型 | 记什么 | 例子 |
|---|---|---|
| `did` | 做了什么，**结果是什么** | `改 main.py 加重复惩罚 → 5 条断言通过` |
| `pit` | 已解决/已知的坑：**识别特征 + 处理法** | `中文 PDF 文本层按列倒序 → 提取失败；特征=单字碎片；处理=放弃不重试` |
| `open` | **未解决**的问题，带最小复现 | `smoke_test 第 3 例 flaky（复现：连跑 5 次 1 次失败）` |
| `next` | 下一步（**单独一段，覆盖语义**） | `补第 4 例` |

三条硬纪律由**代码**强制，不是风格建议：

1. **条目必须单行。** 长串输出、代码块、diff 原文在结构上就写不进来。
2. **条目长度上限 400 字符**（`--max-entry` 可调）。超了直接报错，逼你写成「指令 + 结果」。
3. **只允许一种改写：`open` → `pit`。** 其余只能追加。

## 报错生命周期（这套东西的核心）

```
        出现报错
           │
           ▼
   open #9  <报错原文 + 最小复现>      ← 未解决，这时留全信息
           │
     问题解决了
           │
           ▼
   resolve 9 --keep "特征=…；处理=…"
           │
           ▼
   pit  #9  <特征 + 处理法>            ← 报错原文被丢弃
```

为什么这样设计：

- **未解决时必须留全** —— 这时报错原文就是下一步的输入，压掉它等于让你从零复现。
- **解决后必须只留结论** —— 原文对"下一次生成"不再有信息量，它只是每轮被重发的负担。
  真正值钱的是「这类问题的识别特征」和「当时怎么处理的」，因为**下次还会遇到同类问题**。
- `resolve` **强制要求 `--keep` 文本**，没有默认值 —— 如果没有这一步，
  实现会自动退化成"把报错原文留着"，而这正是要治的病。

## 任务 ID 规则

与 lmmarr 完全一致：字母数字开头，只含 `[A-Za-z0-9._-]`，且不得包含 `..`。
越界的 id 会被拒绝（退出码 2），**什么都不写** —— 这是路径穿越的唯一防线。

## 格式契约（与 lmmarr）

本 skill 自包含，**不依赖** dsh-lmmarr 被安装。但它读的是同一份文件、同一套 frontmatter：

```
---
id / title / status / progress / updated / tags / summary
---
```

`tests/taskdoc.test.js` 用 lmmarr 真实渲染出的样本钉住这个契约 ——
一旦 lmmarr 改了渲染形状，那条测试会红，提醒两边对齐，而不是安静地读出空任务名。
