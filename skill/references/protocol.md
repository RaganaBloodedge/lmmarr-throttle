# 执行器输出协议

**目的**：把「只回结论」从纪律变成结构。

纪律会破功 —— 第一次赶时间就会把 2000 字符的原始输出贴回来。
所以本 skill 的所有执行器都遵守同一套输出形状，让**卸载是结构强制的**。

## 形状

```
成功（退出码 0）：
OK    <一行结论>
KEY   <关键字段>=<值>        × 最多 8 行
DETAIL <路径>                ← 中间过程写文件，要看时再去读

失败（退出码 1，IO / 执行类）：
FAIL  <一行原因>
FIX   <建议动作，或最小复现>
<原始输出，整段，不截断>

用法错误（退出码 2，参数 / 校验类）：
同上形状 —— 与「执行失败」区分开，便于 shell 分支
```

**成功态恒定压在 10 行内。** 超过时被牺牲的是中间的 `KEY` 明细，
`OK` 结论与 `DETAIL` 指针永远保留。

## 退出码约定

| 码 | 含义 | 例子 |
|---|---|---|
| 0 | 成功 | — |
| 1 | 执行失败（IO、外部依赖） | 文件不存在、没有写权限 |
| 2 | 用法 / 校验错误 | 参数缺失、任务 id 非法、条目超长 |
| 3 | `--require` 下能力不可用 | 无子代理（`agents-probe --require`） |

## 双模：为什么失败时反而要吐全量

因为**成功态卸载是有收益的，失败态卸载是有害的**。

成功时，中间过程只是占地方；失败时，中间过程就是调试信息本身 ——
把它压掉，模型就只能靠猜，于是要多花好几轮去复现，反而更贵。

所以：

- 成功 → 压到 ~10 行
- 失败 → 原因 + 修法 + **整段原始输出**

## 怎么写一个新的执行器

1. 从 `scripts/protocol.js` 里 `import { ok, fail, failUsage }`；
2. 参数不够 → `failUsage`（退出 2），IO 失败 → `fail`（退出 1）；
3. 成功路径只 `console` 一行结论 + 至多 8 个 KEY，明细写文件并给 `DETAIL` 路径；
4. **不要**在成功路径里打印原始数据。

判据：**同一个操作你写到第二次，就该固化成执行器。** 预置的执行器源码 0 次进上下文；
现场写的脚本要先花几十行进历史，再被重发几十次才摊得平。
